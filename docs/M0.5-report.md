# M0.5 Technical Spike Report

## 1. Executive Summary

Tide 的核心链路被真实验证并跑通：

> **真实 Torrent → librqbit 9.0.1 → 本地 Gateway（Range/206）→ WebView2 `<video>` → 播放 / Seek / 恢复**

自动化实验（`--spike-autorun`，全部真实运行、数据落盘
`%LOCALAPPDATA%\ifuyo\Tide\spike\results-media.json`）给出：
5/5 容器/编码组合播放通过（首帧 20–160 ms，seek 22–48 ms）；
Torrent→Gateway→WebView2 全链 `ok: true`（1280×720，seek-to-50% 19 ms，
播放恢复）；Gateway 安全矩阵 12/12 集成测试通过；librqbit 渐进读取
（未完成数据阻塞等待 + 字节精确）由集成测试证明。

**结论对应退出条件 A：`Torrent → Resource → Gateway → WebView2` 可稳定工作**（含下述诚实边界）。

## 2. Environment

- Windows 11 x64 (10.0.26200)、WebView2 (Chromium/Edge 154)
- Tauri 2.12.1、librqbit 9.0.1（锁定）、rusqlite 0.37、tokio 1.x
- Node 24 / pnpm 12 / Rust 1.99 MSVC
- 测试媒体全部由 ffmpeg 本地合成（`scripts/generate-test-media.sh`），无任何第三方版权内容

## 3. FACTS

- M0 骨架完整（Task/SQLite/IPC/安全基线）；M0.5 前无任何播放/Torrent 代码
- librqbit 9.0.1 API 已对照 vendored 源码核实（模块私有、根导出、tokio trait、信号量预算）
- WebView2 autoplay 策略需 `additionalBrowserArgs` 配置（实测）
- Chromium 媒体加载行为：并发 Range 连接（头流 + EOF moov）、主动断连、bytes=N- 为主

## 4. Hypotheses

| # | 假设 | 结果 |
|---|---|---|
| H1 | librqbit 库形态支持渐进读取与 seek 优先 | **证实**（FileStream 阻塞语义 + 集成测试字节精确） |
| H2 | WebView2 可直接播 MKV | **证实** |
| H3 | WebView2 需要原生播放器兜底才能覆盖目标格式 | **否证**（矩阵全过；HEVC 条件性） |
| H4 | Gateway 需按 session 串行请求 | **否证**（并发请求是硬需求，串行会死锁元数据） |
| H5 | muted 自动播放在 WebView2 默认允许 | **否证**（play() 永久 pending，需 browser-args） |

## 5. Experiments

### E1 WebView2 Local Playback — **PASS**（5/5 组合，见 M0.5-media-compatibility.md）
### E2 HTTP Range — **PASS**（请求序列 + 206/416 + 测量见 M0.5-http-range.md）
### E3 Torrent Metadata — **PASS**（create/list/seed 全链 292–422 ms）
### E4 Partial Torrent Read — **PASS**（集成测试：未完成数据阻塞读取、字节精确、下载不饿死）
### E5 Torrent Seek — **PASS**（中段/尾部 range 在下载完成前读取正确；UI 侧 seek 50% = 19 ms）
### E6 Multi-file Torrent — **PASS**（4 文件种子，按文件读取无越界，id 越界被拒）
### E7 Tide Gateway — **PASS**（loopback/随机端口/token/Host/Range 矩阵 12/12）
### E8 Full Playback Chain — **PASS**（Torrent→Gateway→WebView2：播放 + seek 19 ms + 恢复，1.4 s 全链）
### E9 Pause / Resume — **PASS**（domain 级测试：暂停停进度、恢复继续、读取不损坏）
### E10 Restart — **PARTIAL（按设计）**：M0 的 SQLite 任务持久化重启恢复已有测试；
spike 的 torrent session/gateway 均为内存态，应用重启后不恢复——
**WHAT WORKS**: 数据库任务/设置跨重启、librqbit 数据文件在盘、应用本身重启无损。
**WHAT DOES NOT**: torrent session / gateway session 的重启恢复（内存态）。
**WHAT M2/M3/M4 MUST DO**: 持久化 session 状态并在启动时 reconcile（M2/M3 范围）。

## 8. Performance Observations

- 首帧（HTTP 环回）：20–160 ms；seek：20–50 ms
- Gateway 读取（完整数据）：256 KiB/chunk，wait_ms = 0
- Torrent 建链 292–422 ms；环回下载 113 MB < 2 s
- 应用空闲内存 ~32 MB；播放期间无异常增长（任务管理器观察，未做系统化 profiling——M9 范围）

## 9. Security Findings

- Gateway 安全边界全部验证：仅 loopback 绑定、随机端口、UUIDv4 token（不可枚举/可过期/可撤销）、
  Host 校验、路径型访问全拒、Range 解析 400/416（12 项集成测试）
- 并发 Range 请求是**功能性安全需求**（串行化=元数据死锁）；修复后按请求克隆资源、独立 FileStream
- CSP 增加 `media-src http://127.0.0.1:*`（仅回环）；无任意 fs/shell 权限引入
- spike 日志只记 id/事件/range 数值，无用户数据

## 10. Architecture Findings

1. `ReadableResource` 抽象成立（File/Torrent/Http 单一 gateway 实现）
2. 每次 range 读取 = 独立 FileStream（librqbit 流与信号量预算约束）
3. `TideError` 增加 `Security` 变体（设计预留类别）
4. mpv/FFmpeg 未引入（无证据需求）；未创建 ifuyo-core 共享 crate

## 11. Decisions

1. Player：**WebView2 only**（M5 设再评估门槛）
2. Torrent：**librqbit 9.0.1 可作为底层引擎**
3. Resource：**HTTP/Torrent 统一抽象成立**
4. Gateway：**值得成为 M4 正式核心层**
5. Seek：**Seek→Range→Resource→Demand 链成立**
6. Playback：**PlaybackSession 独立于 DownloadTask（维持 M0 模型）**

## 12. Rejected Alternatives

libmpv/FFmpeg 现阶段集成（无实测格式缺口 + 许可证审计成本）；MSE 管线（无需求）；
ifuyo-core 共享 crate（无稳定重复）；外部播放器（违背本地一体化定位）。

## 13. M1 Impact

- HTTP 下载可直接复用 fixture server 的流式写出模式（64 KiB 有界 chunk）
- Range 解析器（spike/range.rs）是生产候选，M1 Range 下载与 M4 Gateway 共用语义
- 新增事实：`TideError::Security` 变体已就位

## 14. M3 Impact

- librqbit 9.0.1 锁定有效；Adapter 接口按 spike 的 `TorrentSpike` 面收窄
- **必须**处理：stale 状态下初始化挂起（绑定超时/预校验）、FileStream 生命周期与信号量预算、
  `overwrite` 语义显式化
- Sharing policy 等安全默认值不受 spike 影响

## 15. M4 Impact

- Gateway 直接升级 spike 版本：并发按请求服务（已修）、token/host/range 模型（已测试）、
  换正式 HTTP 栈（当前为手写 HTTP/1.0 级，仅 spike）
- Resource 层：spike 枚举分发已验证够用；Demand/Scheduler 插入点 = `read_range` 的阻塞等待处
- 可用性存储（piece 对齐）仍未建模（M4 主体）

## 16. M5 Impact

- 保留 `--autoplay-policy=no-user-gesture-required`（或显式手势门控）
- 事件监听必须先于 `src` 设置；readyState 探测先于事件等待
- `MediaCapabilityDiscovery` 运行时探测（HEVC 条件性）+ 优雅错误 UI
- 播放器 UI 直接基于本次验证的 `<video>` 事件模型

## 17. Known Limitations

- 环回种子下载过快：UI 全链是在“本地已完成”的 torrent 上播放的；**未完成数据的前沿读取语义由
  集成测试（字节精确）与 gateway 读取日志证明**，UI 上“边下边播未完成区”的可视演示需要限速种子
  （slow-mode 旋钮已备，seeder 限速属 M4）
- HTTP/1.0 级手写服务器（fixture/gateway）仅为 spike；正式版需真正 HTTP 栈
- E10 重启实验为 PARTIAL（见上）；性能观察为非系统化
- 慢网 E11 实验：slow-mode 曾启用（200 ms/chunk）未见 stall（本地完整数据），真实慢源场景留待 M4

## 18. Follow-up Risks

1. HEVC/AC-3 机器差异 → M5 能力探测 + 优雅降级
2. librqbit 升级（9.0.1 → 未来版本）需重跑 spike 式验证（stale-state 行为尤其）
3. WebView2/Edge 策略更新可能改变 autoplay/媒体行为（browser-args 依赖需在 M10 固化审计）
4. 大文件（multi-GB）+ 慢 peer 的 seek 延迟未测——M4 Scheduler 的输入数据

# M0.5 — Torrent Streaming Findings (Experiments C/D/E/F/I)

Engine: **librqbit 9.0.1** (locked in Cargo.lock; API verified against
the vendored crate source, not against docs or blog posts).

## What was verified (all measured on this machine)

| Capability | Result | Evidence |
|---|---|---|
| Create .torrent from file/dir | PASS | `Session::create_and_serve_torrent`, 113 MB hashed in ~200 ms |
| Seed + download via loopback peer | PASS | two sessions, `initial_peers`, no tracker, no DHT |
| Metadata + file listing | PASS | `ManagedTorrent::with_metadata` → `file_infos` (name/len/offset/piece range) |
| File selection | PASS | `AddTorrentOptions.only_files`; bounds-checked ids tested |
| Progressive read of INCOMPLETE data | **PASS** | integration test reads head/mid/tail of an 8 MB payload byte-exact while download is running; reads WAIT for pieces |
| Seek semantics on partial file | **PASS** | mid-file + end-file ranges read correctly before download completes |
| Download continues during reads | PASS | progress advances after reads (asserted in test) |
| Multi-file torrent | PASS | 4-file torrent; per-file reads correct; no cross-file access |
| Pause / Resume | PASS | `Session::pause`/`unpause`; reads recover after resume |
| Streaming prioritization | PASS (implicit) | `ManagedTorrent::stream(file_id)` registers the file as "streamed" (librqbit queues its pieces first); observed as instant reads on the streamed file while background download continues |

## API facts that shaped the design (librqbit 9.0.1)

- `FileStream` implements **tokio** `AsyncRead + AsyncSeek` (not
  futures), is `Unpin`, and blocks reads until required pieces arrive —
  exactly the progressive-read primitive Tide needs.
- The `FileStream` type is **crate-private** (`mod torrent_state` is
  private); consumers must use `impl Trait` returns or trait objects.
- `Session`, `AddTorrent*`, `ListenerOptions`, `ManagedTorrent` are
  re-exported only at the crate root.
- FileStream construction takes a **blocking-semaphore permit**
  (default 8 per session): FileStreams must be short-lived or bounded —
  holding many drains the session's blocking budget. The spike opens one
  stream per ranged read and drops it after.

## Gotchas hit during the spike (all measured, all worked around)

1. **Stale download state can stall `add_torrent` indefinitely** in the
   app runtime: with a previous complete/partial file present and
   `overwrite: false`, initialization hung before returning (no error,
   no progress — observed twice, 8+ minutes). With a clean download dir
   the identical call returns in ~260 ms. Workaround in the spike:
   wipe the download dir per run + 120 s bound on harness setup.
   **M3 MUST**: bound or pre-verify this path, and always set
   `overwrite` deliberately.
2. **`wait_until_initialized`** resolves quickly with full metadata
   (~50 ms) but has no internal timeout — wrap it.
3. `Id20` implements `as_string()` (no `Display`); torrent bytes come
   from `CreateTorrentResult::as_bytes()`.
4. DHT and trackers are default-ON; the spike disables both
   (`SessionOptions { dht: None, disable_trackers: true }`) and binds
   TCP to `127.0.0.1:0` — fully local, license-clean experiments.

## Measured numbers

- Torrent setup (create + seed + add + metadata): **292–422 ms** in-app
  (113 MB source).
- Loopback download of 113 MB: **< 2 s** (bandwidth-bound, ~60 MB/s+
  effective including hashing).
- Progressive reads: `wait_ms: 0` once pieces exist; reads on missing
  pieces block until arrival (semantics verified by test with byte-exact
  assertions).

## Honest scope note

On a loopback seeder the torrent completes before playback starts, so
the UI chain exercised a *complete* torrent; the *incomplete-read*
semantics are proven at the resource layer by integration tests and by
the gateway's ranged-read event log (`wait_ms` per 256 KiB chunk).
A throttled remote-style seeder (slow-mode knob exists on the gateway;
seeder rate-limiting is available via `LimitsConfig`) is the natural M4
follow-up for visually demonstrating mid-download seek in the UI.

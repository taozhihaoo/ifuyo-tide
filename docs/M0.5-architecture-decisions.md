# M0.5 Architecture Decisions

Answering the six questions required by the M0.5 milestone
(each backed by the experiments in M0.5-report.md).

## 1. Player

**WebView2 only** for M5. All matrix formats play/seek; HEVC is
conditional and probeable. Native fallback (libmpv) stays out unless
M5 telemetry shows a real codec gap (see M0.5-player-decision.md).

## 2. Torrent Streaming

**librqbit 9.0.1 is sufficient** as Tide's torrent + progressive-read
engine. Verified: metadata, file listing/selection, sequential and
seek-oriented piece fetching through `ManagedTorrent::stream(file_id)`,
blocking reads on missing pieces, pause/resume, multi-file.
Constraints discovered (documented in M0.5-torrent-streaming.md):
stale-state initialization stall (bound it), blocking-semaphore budget
(bound stream lifetimes), crate-private FileStream type (impl Trait /
adapter boundary). None are architecture-breaking; all fit behind the
planned M3 `TorrentEngine` adapter.

## 3. Resource

**HTTP and Torrent unify under one read interface** — validated by the
spike `SpikeResource` enum (`File` / `Torrent` / `Http`) behind
`len() / read_range(range) / availability(range) / content_type()`,
served by ONE gateway implementation regardless of source. The M4
production shape differs in one respect: the spike used enum dispatch
because async-trait dyn objects were deliberately avoided; M4 should
use a proper async trait (or keep enum dispatch — measured as adequate)
— either way the gateway/player code does not branch on source type.

## 4. Gateway

**A Tide-local Progressive Gateway is justified as the M4 core layer.**
Evidence: loopback-only + random port + UUIDv4 session tokens +
Host/Range validation all pass their security matrix (12 integration
tests); Chromium's concurrent range-request pattern is served
correctly after the per-request resource model fix; measured play +
seek through the gateway from torrent storage works end-to-end.

## 5. Seek

**The chain Player Seek → HTTP Range → Resource.read(range) →
Availability wait → engine fetch is VALIDATED.** Gateway logs show
browser seeks translating into new ranged requests; resource tests
prove reads into undownloaded ranges wait for pieces and return
byte-exact data; the UI seek-through-gateway measured 19 ms on
complete data. The Demand/Scheduler layer (M4/M7) sits exactly at the
measured seam: `read_range` blocking is where demand-driven priorities
will plug in, without changing the interface.

## 6. Playback

**PlaybackSession remains independent of DownloadTask** — validated:
the spike opened gateway sessions against torrent resources without
touching task state; sessions are created/destroyed
(expiry + revocation tested) while the download continues
(asserted in tests: progress advances during reads). The M0 model
needs no structural change.

## Additional measured findings that constrain M4

1. WebView2 media loads issue **concurrent** range requests (head +
   moov-at-EOF) — per-session request serialization deadlocks metadata.
2. Edge autoplay policy leaves `play()` pending even when muted —
   keep `--autoplay-policy=no-user-gesture-required` or require a
   gesture (config exists in tauri.conf.json).
3. Media event listeners must be attached before `src` is set (events
   fire within milliseconds on local sources).
4. librqbit initialization with stale on-disk state can hang — M3 must
   bound/re-verify that path.
5. CSP needs `media-src http://127.0.0.1:*` (loopback only) — implemented.

## Spike code disposition

- **Production candidates** (move to real modules in M4, semantics
  kept): `spike/range.rs` (parser, fully tested), gateway security
  model (loopback/token/host/range), `ReadableResource` interface
  shape, fixture-server streaming pattern.
- **Spike-only** (delete before M4 productionizes): spike frontend
  experiment driver, autorun harness, TorrentSpike dual-session
  seeding fixture (M3 builds the real engine properly), events store.
- None of the spike code leaked into `core/` — the only core change is
  `TideError::Security` (a variant the design reserved anyway).

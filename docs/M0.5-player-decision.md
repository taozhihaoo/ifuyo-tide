# Player Decision

## Environment

- Windows 11 x64, build 10.0.26200
- WebView2 Runtime (Chromium/Edge 154.0.0.0)
- Tauri 2.12.1, `--autoplay-policy=no-user-gesture-required`
- No third-party codec packs; HEVC present on this machine (played)

## Tested Formats

MP4/H.264/AAC · WebM/VP9/Opus · WebM/AV1/Opus · MKV/H.264/AAC ·
MP4/HEVC(hvc1)/AAC — all 640×360 90 s self-made fixtures, loaded over
ranged HTTP and (for the chain test) over the Tide gateway from torrent
storage.

## Passed

- All five container/codec combinations: load, play, pause, mid-file
  seek, duration/currentTime reporting.
- HTTP Range progressive playback (fixture server).
- Torrent → Tide Gateway → `<video>` full chain (1280×720, 120 s file).
- MKV plays directly — no remux needed for H.264/AAC Matroska.

## Conditional

- **HEVC**: played on this machine; support is machine-dependent
  (OS codec/hardware). Requires runtime capability probing in M5.
- **AV1**: software-decode path in WebView2 on machines without AV1
  hardware; worked here (latency within 1.5× of VP9).

## Failed

- Nothing at the container/codec level. (One harness-level failure was
  initially misread as codec failure: Edge autoplay policy leaves
  `play()` pending — resolved by the WebView2 browser-args setting, not
  a format issue.)

## Seek Results

- HTTP ranged: 22–48 ms to 50 % (local disk).
- Torrent through gateway: **19 ms** to 50 % (locally complete); seek
  into not-yet-downloaded ranges verified at resource level
  (byte-exact, blocking-until-available).

## Progressive HTTP Results

See M0.5-http-range.md — browser issues concurrent range requests,
aborts connections freely, plays with T_first_frame 20–160 ms.

## Progressive Torrent Results

Full chain PASS: torrent → gateway → `<video>` play → seek → resume,
chain wall time 1.4 s, first frame after metadata within one refresh.
Ranged reads through the gateway: 256 KiB chunks, `wait_ms` 0 with
locally-present pieces.

## Risks

1. HEVC/AC-3 coverage is machine-dependent → runtime probing +
   graceful error UI (M5), native fallback decision deferred until M5
   data exists.
2. Edge autoplay policy is a per-webview setting — must stay in the
   config; a regression silently pendings `play()`.
3. Long-file seek (multi-GB, slow remote peers) not yet measured —
   M4 scheduler work.

## Decision

**DECISION: WebView2-only** (for M5), with a defined re-evaluation
gate: if M5's real-format telemetry shows > a few percent of playback
attempts failing on codec grounds, revisit `WebView2 + libmpv
fallback` — libmpv stays OUT of the codebase until that evidence
exists (license audit obligation documented in the design spec §75).

## Reason

Every target container/codec in the M0.5 matrix plays, seeks and
progressively streams through Tide's own gateway with sub-100 ms first
frames. The only conditional case (HEVC) is probeable at runtime. No
second player backend is justified by evidence today.

## Consequences for M4/M5

- M4 gateway: must support concurrent ranged requests per session
  (measured requirement), bounded streaming chunks, wait-for-piece
  reads with per-request timeouts.
- M5: runtime `MediaCapabilityDiscovery` (can-play probing), graceful
  codec-error UI, keep the autoplay browser-arg, pre-attach media event
  listeners before setting `src` (events fire within ms on local
  sources).

## Rejected Alternatives

- **libmpv now**: no measured codec gap justifies the license audit and
  process complexity yet (design spec §36/§75).
- **MSE-based pipeline**: unnecessary — plain `<video>` + range server
  covers the formats; MSE would add complexity for zero measured need.
- **External player hand-off**: violates the local-first integrated
  experience; not considered.
